# 第 9 章　递归：把大问题变小

黔灵山公园有条长长的登山步道——九曲径，从山脚一路盘到弘福寺，要爬一千多级台阶。小黔站在第一级台阶前，跟老周打赌：一次迈 1 级或 2 级，爬完这一千多级，一共有多少种走法？路边石栏上蹲着一只猕猴，像在等他的答案。

他先从小的数起：1 级台阶只有 1 种走法；2 级可以"1+1"或"一次迈 2 级"，2 种；3 级呢？"1+1+1""1+2""2+1"，3 种。4 级他数到 5 种，5 级数到 8 种，数着数着就乱了。

"你数出来的 1、2、3、5、8……看出来没有？"老周说，"每一级台阶的走法，都等于前两级走法加起来。因为最后一步，要么是从上一级迈 1 级上来的，要么是从上两级迈 2 级上来的。"

小黔一拍脑袋："那我不用一级一级数了，我只要知道前两级有几种走法就行！"

"对咯。剩下那么多级？先莫急，一哈儿就想通了。"（一哈儿：贵阳话，表示"一会儿"。）

小黔还是有点将信将疑：一千多级那么多，凭什么用两个小一点的数就能算出来？老周让他先在纸上把 1 到 6 级的走法列出来，看看这个规律是不是真的成立。

把"一千多级"的问题，变成"少一级"和"少两级"的问题。再变成更小的问题，直到变成"1 级"这个一眼就知道答案的问题——这就是**递归（recursion）**。这一章我们讲清楚：递归怎么写、程序里到底发生了什么、它为什么容易爆炸，以及什么时候该把它改成循环。

> **本章学习目标**
> ① 会写递归函数，能说清终止条件、递推关系、参数含义这三要素；
> ② 能跟着画出一小段递归的调用过程，明白"压下去、再弹回来"是怎么回事；
> ③ 知道递归的两大代价——重复计算和栈溢出，能判断什么时候该改用迭代。

## 9.1 递归三要素：终止条件、递推关系、参数含义

递归就是函数自己调用自己。听起来像个死循环，但它能停下来，因为你必须准备三样东西：

- **终止条件（base case）**：什么时候直接给答案，不再往下问。爬台阶里是"剩下 1 级时只有 1 种走法"。
- **递推关系（recursive relation）**：大问题怎么用小问题的答案拼出来。爬台阶里是 `f(n) = f(n-1) + f(n-2)`。
- **参数含义**：每个参数到底代表什么。这是最容易被忽略、也最容易写错的一条。

三样缺一不可：没有终止条件，递归停不下来；没有递推关系，大问题接不上小问题；参数含义不清，边界就会写错。

参数含义为什么重要？以爬台阶为例，`f(n)` 的定义是"还有 n 级没爬时，有多少种走法"。如果中途把它理解成"已经爬了 n 级"，终止条件和递推方向就全反了。写递归之前，先在心里把这句话说完整：**我的函数，输入是什么，输出是什么**。说清楚了再动手。

参数还决定了递归什么时候停止。如果参数每次变化的方向不明确，递归就可能原地打转。检查方法：盯着递归调用里的参数，问自己"它是不是每次都离终止条件更近"。`climb(n)` 每次减 1 或减 2，`hanoi(n)` 每次减 1，`gcd` 的第二个参数严格变小——都满足。

写代码的顺序也固定：先写终止条件，再写递推关系，最后检查参数有没有越界。顺序反过来，很容易写出不终止的递归。写完再用最小的几组数据手算一遍：爬台阶先手算 `f(0)=1`、`f(1)=1`，再验证 `f(2)=f(1)+f(0)=2`、`f(3)=f(2)+f(1)=3`，和例题里数出来的一致，说明递推式没写反。五分钟的手算，能省掉半小时的调试。

### 例题 9-1　爬黔灵山台阶（有多少种走法）

**题目**：从山脚到弘福寺一共 n 级台阶，一次可以迈 1 级或 2 级。问爬完这 n 级台阶一共有多少种不同的走法。

**输入格式**：一个整数 n。

**输出格式**：一个整数，表示走法总数。

**样例 1**

输入：
```
4
```
输出：
```
5
```

**数据范围**：1 ≤ n ≤ 30。

**思路**：设 `f(n)` 表示"还剩 n 级台阶时的走法数"。最后一步只有两种可能：迈 1 级，或者迈 2 级。所以 `f(n) = f(n-1) + f(n-2)`。

终止条件有两个：还剩 1 级时 1 种走法（迈 1 级）；还剩 0 级时 1 种走法（什么都不做，这也算一种"完成"）。把 0 也算进去，递推式在 n = 2 时才不会缺项。

**代码**：

```cpp:ch09_ex1.cpp
#include <iostream>
using namespace std;

// f(n)：还剩 n 级台阶时的走法数
long long climb(int n) {
    if (n <= 1) return 1;                 // 终止条件：0 级或 1 级都只有 1 种
    return climb(n - 1) + climb(n - 2);   // 递推关系：最后一步迈 1 级或 2 级
}

int main() {
    ios::sync_with_stdio(false);
    cin.tie(nullptr);

    int n;
    cin >> n;
    cout << climb(n) << "\n";
    return 0;
}
```

**复杂度**：这个问题的时间复杂度是 `O(2^n)`——原因在 9.4 节讲。n = 30 时大约 270 万次调用，还能跑完；n = 40 时大约 3 亿次，明显卡住。空间是递归深度 `O(n)`。

**易错点**：终止条件只写 `n == 1` 不够。n = 2 时 `climb(2)` 会去调 `climb(0)`，如果没有处理 0，就会一路减到负数，递归停不下来。

## 9.2 递归怎么执行：调用栈图解

代码只有两行，但程序里发生的事情不少。我们拿 `climb(4)` 走一遍。

函数被调用时，计算机会在内存里划出一小块地方，存放这次调用的参数、局部变量和"返回后该回到哪一行"。这块地方叫**栈帧（stack frame）**。你可以把它想成函数每次被调用时领到的一张"工位牌"：参数、局部变量、回来该走哪条路，都写在这张牌上。每进一层递归，就压入一个新的栈帧；每返回一层，就弹出一个。

`climb(4)` 的执行过程：

1. 压入 `climb(4)`，它要算 `climb(3) + climb(2)`，先算 `climb(3)`；
2. 压入 `climb(3)`，它要算 `climb(2) + climb(1)`，先算 `climb(2)`；
3. 压入 `climb(2)`，它要算 `climb(1) + climb(0)`，先算 `climb(1)`；
4. 压入 `climb(1)`，命中终止条件，返回 1；
5. 回到 `climb(2)`，再算 `climb(0)`，返回 1，所以 `climb(2)` 返回 2；
6. 回到 `climb(3)`，再算 `climb(1)`，返回 1，所以 `climb(3)` 返回 3；
7. 回到 `climb(4)`，再算 `climb(2)`，注意这里又从头算了一遍，返回 2，所以 `climb(4)` 返回 5。

注意第 7 步：`climb(2)` 被算了两遍（第 3 步和第 7 步）。数据小的时候看不出来，n 一大，这种重复就会失控。

为什么要用"栈"这种东西存？因为递归的规矩是"后进先出"：最后压进去的那层，最先算完返回。这和食堂里摞盘子一样，最后放上去的最先拿走。系统自动替你做了这件事，代价是每一层都要占内存——记住这句话，9.6 节讲爆栈时还要用。

**递归的执行顺序，像爬楼梯再下楼**。一路压到最底下，然后一层一层弹回来；每弹一层，就把子问题的答案交给上一层。写递归的时候，你不需要在脑子里模拟这一整趟；你只要相信"小问题会返回正确的答案"，然后专注于"怎么用它的答案拼出大问题的答案"。

顺便把递归和循环对比一下：循环是"同一个函数、同一块内存，反复用"；递归是"同一个函数、很多块内存，同时活着"。所以递归写起来更像在描述"问题的结构"，循环写起来更像在描述"计算的步骤"，两种描述方式各有各的舒服地方。

## 9.3 递归与数学归纳法：为什么"假设小问题对"就够了

第一次写递归的人，常有一种不踏实感：我只写了"怎么调用自己"，凭什么保证它真的对？

这背后是**数学归纳法（mathematical induction）**。归纳法分两步：第一步证明 n = 1 时成立；第二步假设 n = k 时成立，证明 n = k+1 时也成立。这样一路推上去，所有 n 都成立。

递归的结构和它一模一样：

- 终止条件，对应归纳法的第一步；
- 递推关系，对应归纳法的第二步；
- "假设小问题对"就是归纳假设。

写 `climb` 的时候，你不需要知道 `climb(3)` 内部是怎么算的，你只需要相信：它一定能正确返回 3。基于这个信任，`climb(2) + climb(1)` 就能拼出 `climb(3)` 的答案。只要终止条件正确、递推关系正确，这个"信任链"会一路传到底。

所以递归的正确性，不依赖你在大脑里跑完整棵树。**你只要检查两件事：终止条件对不对，递推关系对不对。** 这两件事对了，整个递归就对了。这也是递归最迷人的地方：代码很短，因为它把"重复的细节"交给了计算机。

这里有个容易绕晕的地方：归纳法里"假设 n = k 成立"并不是真的证明了它。它是一种"如果它成立，那么下一步也成立"的推理。递归函数也是这样：它不管 `climb(3)` 内部怎么算，只负责把 `climb(3)` 和 `climb(2)` 的返回值加起来。只要你检查过终止条件和小规模情况，这条链就一直成立。

经常有人问："递归会不会算错？"答案就是"检查两件事"。如果答案不对，要么终止条件写错了，要么递推关系写错了，几乎没有第三种可能。

## 9.4 递归的代价：斐波那契为什么爆炸

爬台阶的递推式，和斐波那契数列是同一个：`f(n) = f(n-1) + f(n-2)`。斐波那契的递归写法只要三行：

```cpp
long long fib(int n) {
    if (n <= 2) return 1;          // 前两项都是 1
    return fib(n - 1) + fib(n - 2);
}
```

代码漂亮，但它慢得离谱。`fib(40)` 要调用几亿次，`fib(50)` 就要几百亿次，一辈子也算不完。

为什么？看图：

![图 9-1　斐波那契的调用树](assets/fig-09-recursion.png)

图里是 `fib(5)` 的调用树。你会看到 `fib(3)` 出现了两次，`fib(2)` 出现了三次。n 越大，重复出现的结点越多，而这些重复结点的子树会被**重新算一遍**。

算一下量级：每往下走一层，调用次数大约乘 1.6（接近黄金比例 1.618），所以时间复杂度写 `O(2^n)` 是给它一个上界。n = 30 时约 270 万次，n = 40 时约 3 亿次——这不是电脑慢，是方法带来的浪费。

判断有没有重复子问题，有个笨办法：把递归函数的所有参数当成"状态"，数一数不同的状态有多少个。爬台阶只有一个参数 n，状态只有 n+1 个；可朴素递归却算了几百万次，说明每个状态被重复算了很多遍。状态少、调用次数多，就是重复计算的味道。

这个浪费可以避免：`fib(3)` 第一次算出来之后，把答案记下来，第二次直接查表。这个技巧叫**记忆化（memoization）**，是动态规划的开端（第 23 章）。本章只要记住结论：**递归的代码短，不等于它快；有重复子问题的时候，递归可能慢得不可接受。**

有人会想：那我把 n 限制小一点不就行了？问题在于，题目不会因为你写得慢就放过你。第 4 章那张表说 `O(2^n)` 只在 n ≤ 20 左右可用，本题 n = 30 时已经几百万次调用，时间限制一紧就 TLE。所以看到"n 能到 10^5"的题，绝不会是这种朴素递归。

顺带一提，斐波那契还有更快的做法（矩阵快速幂，第 29 章），能把 `O(n)` 压到 `O(log n)`。不过那是后话，现在先把"递归不能乱用"这件事记住。

## 9.5 递归转迭代：从栈的角度看

递归好写，但有时候不能写：数据规模大到会爆栈，或者题目对常数要求很严。这时候可以把递归改成**迭代（iteration）**，也就是用循环。

改的思路，从"栈"的角度看最清楚：递归是把"还没算完的活"存在系统栈里，等子问题返回再取出来接着干；迭代就是你自己用几个变量把这份"存起来的活"记下来。爬台阶的递归是从大往小问，改成迭代后就从小往大算：

```cpp
long long f0 = 1, f1 = 1;          // f(0) = 1, f(1) = 1
for (int i = 2; i <= n; i++) {
    long long f2 = f0 + f1;        // 相当于 f(n) = f(n-1) + f(n-2)
    f0 = f1;
    f1 = f2;
}
cout << f1 << "\n";
```

递归版本算 `f(n)` 时要一路压栈到 `f(0)`，再一路弹回来；迭代版本从 `f(0)`、`f(1)` 开始，一次循环往前推一步，算到 `f(n)` 为止。时间复杂度从 `O(2^n)` 降到 `O(n)`，空间从递归深度 `O(n)` 降到 `O(1)`。

改的时候有个检查办法：列出递归里"哪些量在变"，迭代就要把这些量全部用变量表示。爬台阶只有 n 一个量在变；如果递归还有别的状态（比如第 11 章"当前走到哪个格子"），迭代就得把这些状态都存下来，代码会明显变长。这也是为什么有时候宁可写递归。

不过，不是所有递归都这么好改。斐波那契、爬台阶这类"每一层只依赖前几层"的递归，改成循环很自然；汉诺塔那种"要先处理上面 n-1 个，再处理最大的，再处理 n-1 个"的递归，改成迭代就得自己维护一个栈，反而更复杂。**该不该改，看两件事：会不会爆栈、会不会超时。** 都不会的话，递归写得清楚就先用递归。

### 例题 9-2　汉诺塔（打印移动步数）

**题目**：有三根柱子 A、B、C，A 柱上从下到上摞着 n 个大小不同的圆盘（小盘在上）。每次只能移动一个盘子，而且大盘不能压在小盘上。要把所有盘子从 A 柱移到 C 柱，最少需要移动多少步？

**输入格式**：一个整数 n，表示盘子数。

**输出格式**：一个整数，表示最少移动步数。

**样例 1**

输入：
```
3
```
输出：
```
7
```

**数据范围**：1 ≤ n ≤ 20。

**思路**：把"n 个盘子从 A 移到 C"拆成三步：先把上面 n-1 个盘子从 A 移到 B（借助 C），再把最大的那个从 A 移到 C，最后把 n-1 个盘子从 B 移到 C（借助 A）。每一步又是同样的问题，只是盘子更少、柱子换了。

所以 `hanoi(n, from, aux, to)` 就是"把 n 个盘子从 from 搬到 to，aux 是中转站"。参数含义写清楚，三个参数的顺序才不会搞混。

**代码**：

```cpp:ch09_ex2.cpp
#include <iostream>
using namespace std;

// 把 n 个盘子从 from 移到 to，借助 aux，返回移动步数
long long hanoi(int n, char from, char aux, char to) {
    if (n == 0) return 0;                       // 没有盘子，不用动
    long long cnt = 0;
    cnt += hanoi(n - 1, from, to, aux);         // 上面 n-1 个先挪到中转站
    cnt += 1;                                   // 最大的那个挪一步
    cnt += hanoi(n - 1, aux, from, to);         // 再把这 n-1 个挪到终点
    return cnt;
}

int main() {
    ios::sync_with_stdio(false);
    cin.tie(nullptr);

    int n;
    cin >> n;
    cout << hanoi(n, 'A', 'B', 'C') << "\n";
    return 0;
}
```

**复杂度**：时间 `O(2^n)`，空间（递归深度）`O(n)`。步数恰好是 `2^n - 1`，这也是最少步数。

**易错点**：递归调用里三个柱子参数的顺序是这道题最大的坑。第一步是"从 from 搬到 aux，借助 to"，所以写 `hanoi(n-1, from, to, aux)`——中转站和终点换了位置。写完之后，用 n = 2 手推一遍：`hanoi(2,'A','B','C')` 应该是 3 步，对不上就说明参数顺序错了。

## 9.6 递归的边界：栈溢出、递归深度

递归不是免费的。每压一层栈帧，就要占一块内存。系统给程序分配的栈空间是有限的（常见是几 MB），压得太深就会**栈溢出（stack overflow）**，程序直接崩溃，OJ 上显示 RE 或者"段错误"。

多深会爆？粗略估计：一个栈帧几十个字节，1 MB 大约能压一两万层，8 MB 大约十万层出头。所以：

- `O(log n)` 层的递归，比如最大公约数，n 再大也只有几十层，非常安全；
- `O(n)` 层的递归，n 到 `10^5` 就有点危险，n 到 `10^6` 几乎一定爆栈；
- `O(2^n)` 层的递归，n 到二十几层就爆了——不过这种递归通常也早超时了。

爆栈的解决办法有三个：把递归改成迭代（首选）；把问题规模降下来；或者用编译选项调大栈空间（比赛时一般不让改）。

在 OJ 上，爆栈通常显示成 RE（Runtime Error）或者"段错误"，不会明明白白告诉你"栈溢出"四个字。所以看到递归题 RE，先想想是不是层数太深，不要急着怀疑数组越界。

怎么估算自己的递归深度？数一数递归调用的层数就行：`climb(n)` 最深 n 层，`hanoi(n)` 最深 n 层，`gcd` 最深 log 层。写完递归先数层数，再对照数据范围，这是防止 RE 最简单的习惯。

### 例题 9-3　递归求最大公约数（欧几里得算法）

**题目**：给两个非负整数 a 和 b（不同时为 0），求它们的最大公约数。

**输入格式**：一行两个整数 a 和 b。

**输出格式**：一个整数，表示最大公约数。

**样例 1**

输入：
```
12 18
```
输出：
```
6
```

**数据范围**：0 ≤ a, b ≤ 10^18，a 和 b 不同时为 0。

**思路**：欧几里得算法（Euclidean algorithm）的依据是：`gcd(a, b) = gcd(b, a % b)`。一直除下去，直到 b 变成 0，此时 a 就是最大公约数。这是一个"参数越来越小"的递归，每两层至少减半，所以递归深度是 `O(log n)`，完全不用担心爆栈。

注意 a < b 的情况：`a % b = a`，第一层递归会把两个参数交换过来，不用特意写判断。

**代码**：

```cpp:ch09_ex3.cpp
#include <iostream>
using namespace std;

// gcd(a, b) = gcd(b, a % b)，b 为 0 时答案是 a
long long gcd(long long a, long long b) {
    if (b == 0) return a;          // 终止条件
    return gcd(b, a % b);          // 递推关系
}

int main() {
    ios::sync_with_stdio(false);
    cin.tie(nullptr);

    long long a, b;
    cin >> a >> b;
    cout << gcd(a, b) << "\n";
    return 0;
}
```

**复杂度**：时间 `O(log min(a, b))`，递归深度 `O(log min(a, b))`。空间 `O(log min(a, b))`。

**易错点**：数据范围到 10^18，必须用 `long long`。这题的递归深度很小，是"安全的递归"的典型代表；而爬台阶那种 `O(n)` 层的递归，写之前就要先估一下 n 有多大。

递归是后面几章的地基：分治（第 10 章）是"把问题分成几份，各自递归"；深度优先搜索（第 11 章）是"在每个岔路口递归试探"。本章把递归本身讲清楚，后面两章就是它的两个主要用法。

## 本章小结

> **记住这三句**
> ① 递归三要素：终止条件、递推关系、参数含义，先把这三样说清楚再写代码。
> ② 递归的正确性来自数学归纳法：只要终止条件对、递推关系对，就不用在大脑里跑完整棵树。
> ③ 递归有代价：会重复计算（`O(2^n)`），也会爆栈（层数太深），该改迭代就改迭代。
